## Fixed in this lane (within mandate)

### V1 (P1) — wizard-written rc bootstrap PATH-shadows the running niu — FIXED

- **Repro (pre-fix, base binary, this machine):** stale **Niubash 1.2.5**
  (`C:/Users/Administrator/AppData/Local/Programs/Winuxsh/niu.exe`) is first on
  PATH (`command -v niu` resolves to it). After `niu setup --preset minimal` in a
  sandboxed HOME, every fresh startup printed:
  ```
  $ niu.exe -C 'echo rc-noise-probe-done'
  niu: unknown plugin subcommand 'sync'      <-- from the 1.2.5 on PATH
  rc-noise-probe-done
  ```
  The 1.2.5 predates `plugin sync`; worse, when the PATH niu is a different vintage
  that *has* sync, the startup reconcile runs under the wrong binary's semantics
  against the shared spec/registry.
- **Owner (read-only attribution):** rc template
  `crates/niubash-runtime/src/setup_wizard.rs` `generate_rc()` (bootstrap line);
  fix direction verified against `src/main.rs` `run_main()` which exports
  `NIU_SHELL` (and deprecated `WINUXSH_SHELL`) from `std::env::current_exe()`
  before `run()` — so `NIU_SHELL` is always the running exe inside any niu process
  that sources the rc, and inherited by engine child shells.
- **Fix applied:** the template now emits
  ```sh
  command -v "${NIU_SHELL:-niu}" >/dev/null 2>&1 && "${NIU_SHELL:-niu}" plugin sync --bootstrap
  ```
  with a comment naming the why. Fallback to bare `niu` preserves today's behavior
  for plain `source ~/.niubashrc` from foreign shells; if `NIU_SHELL` is set but the
  exe was moved/deleted, `command -v` fails and the line skips silently (strictly
  better than reconciling under a stale binary). Assertion in
  `generated_rc_is_clean` updated to pin the exact emitted line.
- **Verification:** with a PATH-shadowing stale niu (real 1.2.5, and a synthetic
  `cmd.exe`-as-`niu.exe` fixture), `niu -C 'echo marker'` output is clean and the
  marker is present (`sweep.sh` probes `v1-startup-clean-under-stale-path`,
  `v1-wizard-emits-niu-shell-line`). Sandbox rc written by the fixed wizard contains
  the NIU_SHELL line; `-c`/`-C`/REPL-shaped invocations all clean.
- **Doctor check added (advisory row, does not count toward critical N/M):**
  `crates/niubash-runtime/src/doctor.rs` — `find_niu_on_path()` walks PATH
  (`.exe/.bat/.cmd/.com` + extension-less, mirroring what `command -v` resolves),
  `same_executable()` compares canonicalized (case-insensitive fallback) against
  `current_exe()`. On mismatch:
  ```
  ADVICE niu on PATH  C:/Users/Administrator/AppData/Local/Programs/Winuxsh/niu.exe
    is NOT this niu (D:/repo/niubash-wt-L01/target/release/niu.exe) — bare `niu` and
    the rc bootstrap run the PATH copy; update/reinstall it (`niu --self-update` from
    that copy) or reorder PATH so the current install wins
  ```
  Fires only on mismatch (silent when PATH niu is this niu or absent). The row
  fired on this machine's real 1.2.5 shadow during the L22 sandbox run — true
  positive.
- **Migration note — existing rcs in the wild have the bare form.** Every rc already
  written by 1.3.0–1.3.3 (and this line in `.niubashrc.example`-style copies) carries
  `command -v niu >/dev/null 2>&1 && niu plugin sync --bootstrap`. The wizard only
  fixes NEW writes; existing users need the one-line patch:
  ```sh
  # sed one-liner (bash, LF rc):
  sed -i 's|^command -v niu >/dev/null 2>&1 && niu plugin sync --bootstrap$|command -v "${NIU_SHELL:-niu}" >/dev/null 2>\&1 \&\& "${NIU_SHELL:-niu}" plugin sync --bootstrap|' ~/.niubashrc
  ```
  or by hand: replace both `niu` occurrences with `"${NIU_SHELL:-niu}"`. Detection:
  `niu doctor` now prints the mismatch row whenever a PATH-shadow exists; a fix lane
  could also reconcile the bare form in-place at startup (not done here — read-only
  mandate). Untouched rcs are not *broken* by the omission: they simply keep today's
  behavior, and the doctor row names the hazard.

## L22 migration findings (read-only; sandbox-reproduced)

Fixture built from the v1.2.5 tag (`niubash.git 3d0de1e`): 1.2.x-shaped rc + the
wt45 dead fields (`NIU_THEME`, `NIU_THEME_PLUGIN`, `NIU_PLUGINS`, `NIU_BANNER`,
`NIU_PROMPT_SYMBOL`) a README-era user would carry; registry at
`niubash:plugin-source-registry@0.1.0` with a 1.2.5 record shape (verified: all
1.3-era fields are `#[serde(default)]`, and 1.2.5's `previous` = `{ref, version,
checksum_sha256}` still parses); pre-spec imperative trees under
`~/.niubash/sources/`; no `plugins.toml`; `.setup-done` marker present.

### Migration surfaces that behave correctly (verified, no action)

- **`.winuxshrc` → `.niubashrc` migration once-only.** First `-C` contact migrates
  (target written, `WINUXSH_*`→`NIU_*`, `winuxsh.exe`→`niu.exe`, `.winuxshrc`
  self-references rewritten), original file byte-untouched, second run changes
  nothing (`shell.rs migrate_legacy_winuxsh_rc`: skipped when target exists).
- **Registry version bump is lazy and lossless.** First contact with an @0.1.0
  registry does NOT rewrite it (schema stays @0.1.0 until a verb writes); the 1.2.5
  row is preserved and visible in `plugin list` / `doctor`.
- **Spec absence = imperative mode, silent.** No spec at boot: no error, no spec
  written, `plugin sync` prints one informational line.
- **Dead rc fields harmless.** `NIU_THEME`/`NIU_PLUGINS`/… produce no errors, no
  retired-stack semantics, rc sources clean.
- **Backups.** First contact does not touch the 1.2.x rc (nothing to back up);
  the wizard re-run over the vintage rc creates
  `~/.niubash/backups/.niubashrc.<stamp>.bak` carrying the full vintage content
  (real restore path).
- **First contact completes**: `-C` alive, no panic, no plugin noise, second run
  stable.
- **V1-in-migration (post-fix):** after the wizard re-run, startup under a
  PATH-shadowed stale 1.2.5 is clean (`s2-post-upgrade-clean-under-stale-path`).

### M2 (P1) — unparseable registry reads as empty, and a successful `sync` destroys its rows — REPORTED, NOT FIXED

- **Repro** (`scripts/audit/l22-migration/migrate.sh` scenario 3; the
  `s3-sync-preserves-unreadable-rows` FAIL in the current run IS the finding — it
  doubles as M2's regression check and will go green when a fix lane lands):
  1. Seed `~/.niubash/sources/registry.toml` with one row whose shape fails to
     deserialize (here: `previous` missing the required `ref` — corruption,
     hand-edit, or future vintage skew reaches the same state).
  2. `niu plugin list` → `(no sources installed)` — the whole registry is
     invisible. The only signal is `log::warn!` (visible only under
     `RUST_LOG=warn`): `failed to parse plugin source registry: TOML parse error …
     missing field 'ref'`.
  3. `niu doctor` → `plugin sources  none installed`.
  4. Put any reconcilable spec in `~/.niubash/plugins.toml` (e.g. one local-path
     source), run `niu plugin sync` → succeeds, prints the reconcile outcome —
     and **rewrites `registry.toml` with only the spec rows. The unreadable row
     (pin, checksum, trust state) is gone.** The tree on disk survives; the record
     does not.
- **Expected (product's own promises):** doctor's degraded-visibility iron law
  ("degraded sources must be *visible*") and the trust/lockfile model (records are
  the restore/rollback pin) — silent empty + blind overwrite breaks both.
- **Actual:** read = silent empty at default log level; write = full overwrite.
- **Suspected owner (read-only attribution):**
  `crates/niubash-runtime/src/plugins/sources.rs:398 read_source_registry()`
  (parse failure → `log::warn!` + empty Vec) and
  `crates/niubash-runtime/src/plugins/sync.rs` `sync_sources()` — `read_source_registry()`
  at `sync.rs:230` then `write_source_registry(registry)` at `sync.rs:480`, with no
  parse-failure guard and no registry backup. Fix direction (not applied): refuse to
  rewrite a registry that fails to parse (preserve bytes, surface an actionable
  error naming the line), and/or back it up before the first write.
- **Severity:** P1 — record loss without consent on a documented verb; reachable
  from corruption/hand-edit (a *clean* 1.2.5 registry is safe — verified), so not
  P0.

### Census observations (P2, report only)

- **`niu plugin sync` exits 0 even when a declared row fails to install**
  (`failed spec-src  git clone exited with status 128`, rc 0). Documented Exit 0 in
  the quickref, so the docs agree — but it is inconsistent with `add`'s
  failed-install honesty ("add must fail when the row failed"). Scripted upgrade
  flows cannot detect partial failure by exit code alone. Owner: `plugins/sync.rs`
  exit-code policy + quickref exit table (D03/D12 classes).
- **Flag admission is inconsistent across lockfile verbs:** `plugin list --bogus`
  and `plugin clean --bogus` silently ignore the flag (rc 0); `plugin update
  --bogus` → `unknown plugin source option` (rc 1, routes into the source-update
  parser); `plugin restore --bogus` → treats the flag word as a source id
  (`unknown source '--bogus'`, rc 1 — honest but names the wrong object class).
  All named errors stay honest; the inconsistency is usage-text hygiene (D06/D11).
- **`niu plugin ui` without a tty** degrades correctly (rc 1 + inline CLI verb
  list) — confirmed positive from the wt74 worked example, now pinned by
  `plugin-ui-nontty`.
- **Environment-bound (not findings):** `--self-update --check` exit code/network
  messages are network truth (this host's TLS inspection produced the V5 repro
  pre-fix and a clean success post-fix within the same session); a fixture-authored
  registry row with an MSYS-style `path` shows as `degraded` (invalid Windows dir)
  — probe artifact, not product behavior.
